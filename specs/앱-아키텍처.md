# 앱 아키텍처

## 선택

Beck이 선택한 Bloc 중심 구성이다.

1. 라우팅: `go_router` + `CupertinoApp.router`. iOS·Android 모두 기본 Cupertino 페이지 전환과 조작을 사용하며, 커스텀 전환은 지정하지 않는다.
2. 상태 관리: `flutter_bloc`, 단순 상태와 비동기 작업은 Cubit으로 시작한다. 이벤트 처리 순서나 동시성 제어가 필요하면 Bloc을 사용한다.
3. 의존성 주입: `RepositoryProvider`와 `BlocProvider`. 의존 객체는 생성자로 전달한다. 별도 `get_it`은 도입하지 않는다.
4. 기능 구성: `features/home`, `features/catalog`. 공통 테마·컴포넌트는 `design_system/`에 둔다.

## 책임과 의존 방향

1. `app/`: 앱 초기화, 앱 범위 의존성 구성, 테마 설정.
2. `routing/`: 경로와 화면 생성. 기능 간 이동을 조립한다.
3. `features/`: 화면·Cubit/Bloc·불변 상태. 화면은 입력을 전달하고 상태를 표시한다.
4. `data/`: 기록 Repository와 실제 저장소 접근. UI나 라우터에 의존하지 않는다.
5. `domain/`: 기능이 공유하는 콘텐츠·추천 모델과 필요한 추천 규칙.
6. 플랫폼 AI 어댑터: iOS·Android의 모델 API 호출과 준비 상태를 담당한다. 추천 후보 선정·검증·대체 추천과 구분한다.
7. `design_system/`: 공통 토큰과 위젯. 기능의 Cubit이나 Repository를 참조하지 않는다.

Repository와 Service를 항상 한 쌍으로 만들지 않는다. 기록 Repository는 로컬 DB를 직접 사용할 수 있다.
추천은 역할에 맞는 Engine으로 구성하며, 외부 호출을 격리할 필요가 있을 때 어댑터를 추가한다.
아직 기능이 없는 계층의 빈 파일이나 인터페이스는 미리 만들지 않는다.

## 수명과 기능 경계

1. 공유 Repository는 앱 범위에서 생성하고 종료 시 해제한다.
2. 기능 Cubit은 기능 진입 영역의 BlocProvider가 생성·해제한다.
3. 기능은 다른 기능의 Cubit을 참조하지 않는다. 공통 데이터는 Repository로 공유한다.
4. 공통 위젯에는 데이터와 콜백을 전달한다.
5. 카탈로그의 샘플 상태는 카탈로그 내부에서만 관리한다. 제품 사용 시나리오와 화면은 아직 확정하지 않았다.

## 현재 구현 범위

현재 기본 실행 화면은 기존 Flutter 카운터 템플릿(`/`)이다. 제목·카운터·증가 기능을 유지하며, Cupertino UI와 디자인 시스템 카탈로그 진입을 제공한다.
`/`와 `/catalog`를 제공한다.
카탈로그는 `features/catalog/`의 독립 화면이며, 첫 화면에는 이동 버튼만 연결한다.
카탈로그는 앱의 Cubit·Repository·콘텐츠 상세 경로에 의존하지 않는다. 공통 테마와 위젯을 사용하며, 테마·글자 확대·샘플 동작은 화면 안에서 관리한다.
새 컴포넌트 예시는 카탈로그의 `sections`에 추가한다. 앱 화면이나 기능 상태를 수정할 필요 없이 다른 진입점에서도 `ComponentCatalogScreen`을 사용할 수 있다.
Bloc 중심 아키텍처 선택은 유지하되, 제품 기능의 Cubit·Repository는 아직 구현하지 않는다. 카탈로그의 예시를 실제 앱 사용 시나리오로 취급하지 않는다.
